# 圧縮配信・ビルドの検証と失敗例

## 使う場面

gzip / Brotli 配信、指紋付き JS/CSS、共有 bundle、公開前に加工される HTML を変更する場合に読む。圧縮形式やファイル命名は既存配信環境に合わせる。以下は一般化した実例であり、特定の CDN やフレームワークの必須設定ではない。

## 最終内容と参照をそろえる

- 圧縮配信用の URL 命名と import・CSS の依存関係を、ビルドの内容 hash 確定前に決める。hash 確定後に import 文字列を書き換えたり、同じ immutable URL の内容を上書きしたりしない。
- 圧縮処理自体は最終バイト列から行ってよい。通常版と圧縮版が対になる構成では、解凍結果が通常版と完全一致することを確認する。参照される遅延 JS/CSS も公開対象に含める。
- SEO 本文の引き継ぎ、更新チェック挿入などで HTML が最後に変わる場合、圧縮 HTML もその加工後に生成する。比較対象はビルド直後でなく、実際の配布パッケージ内の HTML。
- `Content-Encoding`、MIME、`Vary: Accept-Encoding` が必要な構成での変種分離、cache 方針を実応答で確認する。`.gz` の存在だけではブラウザーでの利用を証明できない。通常 JSON への fallback がある場合は正常時と圧縮読込失敗時を確認する。

## 最小の回帰確認

1. 共有 CSS、遅延 import、入れ子のエントリーを含む本番ビルドで、全参照先の存在と MIME を確認する。
2. 配布パッケージ内で圧縮版を解凍し、対応する最終通常版と比較する。
3. ソースを変更して再ビルドし、変更資産とそれを参照する資産の hash が適切に更新されることを確認する。テスト用変更は本番に混ぜない。
4. 公開後の応答とデスクトップ・モバイル表示で図表、SVG、共有メニュー、詳細の遅延表示を確認する。未実施の検証は完了扱いにしない。

## 失敗例と再利用できる判断

| 実際に起きた問題 | 原因 | 修復と確認 |
| --- | --- | --- |
| SVG が巨大化し、メニューの見た目が崩れた | スタイルを供給する CDN を、同等のビルド済み CSS なしで削除した | 権威となるスタイル供給を復元し、置換するなら先に同等 CSS を用意して画面確認する |
| 圧縮 URL への書き換えで参照と hash の意味がずれた | hash 確定後に出力を書き換えた | 命名・参照をビルド依存グラフに組み込み、最終バイト列から圧縮し、内容変更による hash 更新を検証する |
| 通常 HTML と圧縮 HTML に異なる本文が残った | HTML の最終加工前に圧縮していた | 配布用 HTML の加工後に圧縮副本を再生成し、解凍して比較する |

圧縮はネットワークの対策であり、解析・DOM・描画量の上限ではない。共有部品でも実装が別々に同じランタイムを同梱していないか調べる。一覧と詳細の読み込み経路を両方追い、必要な図表を減らすことを性能改善の前提にしない。
