# 重いWebページの原因を調べ、読み込みを軽くする

入力は対象ページ、ソース、利用できる測定環境と変更範囲。出力は実測に基づく優先順位、許可された修正、変更前後の確認結果。サーバー保存量の増加は `data-growth-guard` が担当する。

## 進め方

1. 「評価のみ」「圧縮のみ」「読み込み構造も変更」を依頼から区別する。評価のみなら変更せず、圧縮のみならデータ構造や取得方式の変更へ広げない。実コード、ページ仕様と生成・公開手順を読み、現在の UI とデータの意味を維持する。
2. 初回の HTML、JS/CSS、業務 JSON/API、第三者リソースを分け、実際の転送量とリクエスト数を記録する。解凍後のサイズ、JSON 解析、描画、操作中の再取得も分けて確認し、未測定の項目は明記する。共有部品から詳細ページまで依存をたどり、ランタイムの重複同梱や一覧用 bundle の不要な取得を調べる。
3. gzip ファイルの有無とブラウザーでの利用を分ける。Content-Encoding、MIME、解凍後の内容、通常 JSON への切り替えを実際の読み込み経路で確認する。ローカル圧縮の推計を公開済みの効果と呼ばない。
4. 許可された範囲で効果のある箇所だけ修正する。不要な重複取得、未使用フィールド、圧縮、既存キャッシュの再検証を確認する。分割や事前計算は利用範囲と解凍後の解析・描画負荷からも判断する。圧縮後の転送量が小さくても処理が軽いとは限らない。ページング・圧縮・キャッシュ・遅延読込を同じものとして扱わない。
5. 一覧は必要範囲の再生成可能な投影、詳細は安定 ID と日付などで特定する完全な記録から読む。初回表示しないタブや履歴を全件取得しない。公開期間と原本の保存期間を混同しない。
6. データ形式を変える場合は書き込み側、圧縮副本、読者、公開順序をそろえる。新データを検証してから読者を切り替え、静的配布で本番データを上書きしない。圧縮配信や指紋付き資産を変更する場合は [配布検証と失敗例](references/compression-and-build-checks.md) を読み、最終内容と参照関係を hash 確定前に整え、最終公開物と解凍後の内容を比較する。
7. 本番用ビルドとブラウザーで、デスクトップ・モバイルの図表、メニュー、文字、SVG、ダイアログ、詳細表示を確認する。必要な CSS や図表を削除して軽量化しない。CSS 配信を変更するなら先に同等のビルド済みスタイルを用意する。
8. 公開を伴う場合は実際の応答を再測定する。転送量の減少と操作・描画速度を分けて報告し、改善余地が小さいページは追加改造を勧めない。

既存の圧縮 writer/reader、計算器、公開ツールを再利用する。`data-growth-guard` は保存設計を変える場合、`static-deploy-refresh-check` は配布と生成物保護を扱う場合だけ読む。技能が未導入なら必要な範囲を伝え、呼び出したことにしない。
